調査基準日: 2026-09-25
成果物: ComfyUI-DLSS5-AMD v0.1.0a1、テスト、ワークフロー、ロードマップ。

1. 結論

最初に作るべきなのは、ニューラルネットワーク自体の再実装ではなく、既存 AMD ネイティブホストを、失敗検出と実行証拠つきで ComfyUI に接続する薄いブリッジである。

今回、その接続部分を実装した。採用候補の外部ホストは eikkapine/DLSS5-AMD-Video。公開されている RGBA8 入出力、フレーム単位の処理、完了レポートが比較的明確だからである。ソースの基準コミットを 9303dfaa14c2ca83e237ff18318bdfc0b767f6fb に固定した。[S02–S04]

ただし、これは「すでに 9070 XT で画質が劇的に改善する ComfyUI 製品が完成した」という報告ではない。こちらの環境は Linux・CPU のみであり、Windows/D3D12/HIP の実行、利用者の GPU、正当な権限を持つランタイムを組み合わせた検証は残っている。対応ファイルがない状態では、ノードは理由を示して停止する。

初期方針は次の分離である。

画像の質感・照明の再構成       画像の縦横ピクセル数の増加
Neural Rendering (NR)    →    別の超解像・拡大工程

この二つを混同しないことが、開発と画質評価の前提となる。

2. 前の提案から訂正した点

AMD 版は実証段階をかなり越えている プロジェクトごとに段階が違う。採用候補の動画ホストは実験的で、短い実行確認と画質保証は別
数ミリ秒の速度を ComfyUI でも期待できる カーネル時間・ゲーム統合時間・オフライン全工程は比較条件が違う。今回の性能目標に転用しない
FSR4 を後につなげれば完成 ゲーム由来の補助入力を持たない画像／動画は別条件。初版には組み込まない
ONNX なら容易にそのまま使える 確認した公開モデルは固定 256×256 の静止画再構成で、入力色空間や実行環境の制約がある
AMD ComfyUI ノードは誰も完成させていない 今回の探索で検証可能な完成品を確認できなかった、まで。世界中に存在しないとは断定しない
一晩で v0.1 根拠のない所要時間の約束は撤回。実機テストを含む完了条件で管理する

新しいリポジトリに価値があるのは「名前が空いている」からではなく、Windows/AMD 利用者が、何が動いたのか・何が未確認なのかを判断できる接続基盤を提供できるからである。

3. DLSS 5 NR は普通のアップスケーラーではない

NVIDIA の公式説明は、DLSS 5 を外観・照明・素材感を再構成するニューラルレンダリングとして扱い、Super Resolution、Frame Generation、Ray Reconstruction と独立して組み合わせられる機能として説明している。公式ゲーム統合では、ゲーム側の動きベクトルを利用した時間方向の安定化も説明されている。[S01]

一方、画像生成後の PNG やエンコード済み動画には、通常、そのゲームエンジン由来の入力がない。本プロジェクトが接続する初期経路は color-only / stateless である。[S03]

したがって、次の主張は行わない。

「本ノードは公式 DLSS 5 の完全再現である」「ゲーム内のデモと同じ時間安定性がある」「ピクセルが変わったので画質が改善した」「ファイルサイズが増えたので細部が復元された」。

動画編集用途では、顔・商品・ロゴ・文字・線画の形状維持も重要になる。写実感が増しても、商品形状や文字が変われば、その素材では不採用とする。これは今回の品質評価方針であり、実測済みの効果ではない。

5. 速度をどう解釈するか

動画ホスト作者の報告では、RX 9070 XT、1920×1080、120 フレームの 5 秒素材を扱い、全工程に 408.98 秒、約 3.41 秒／フレームを要した。特定の新しいランタイムと fast-isolated の組合せによる短い測定であり、こちらの測定ではない。[S02]

重要なのは 再生 FPS と処理 FPS の区別である。24 fps の動画を作るのに、各フレームの処理が数秒かかっても、完成動画の再生速度は 24 fps のままである。

この経路は、フレームごとに子プロセスを分離して処理完了を確認する。ニューラルネット単体が高速でも、初期化・メモリ転送・同期・読み戻し・ディスク入出力を含む全工程は遅くなり得る。[S03]

今回のブリッジは最終段を FFV1 の可逆圧縮に変更し、ハッシュ検査も追加している。作者の H.264 出力と全く同じ条件ではない。そのため、3.41 秒／フレームを本実装の性能値としても約束しない。

測定を分離する設計

指標 用途
起動・モデル初期化時間 cold start の負担
GPU 処理時間 実同期点で測定するニューラル処理部分
CPU→GPU→CPU の転送・同期 Python とネイティブの橋渡し負担
画像 1 枚の全工程時間 単画像の操作感
動画全工程時間／実フレーム数 実制作の throughput
ピーク VRAM / RAM / 一時ディスク OOM と容量不足の回避

本版で自動保存しているのは主として壁時計時間と処理記録である。GPU のイベント時間、実 VRAM、長時間メモリリークは未測定。ロードマップに追加した。

    ▼                                │

    │ 固定パスの EXE/DLL/重みを SHA 検証 │
    ▼                                │

    ▼                                │

    │                                │
    ▼                                │

    ▼
ComfyUI IMAGE + 実行記録 JSON

ComfyUI の公式 IMAGE は [B,H,W,C]、MASK は [B,H,W] である。本コードは IMAGE の RGB に加え、CLI や一部ノード向けに RGBA も扱う。MASK の白を「適用」と定義し、LoadImage が返す反転 alpha と混同しない。[S09]

PyTorch/ROCm を破壊しない

本版は PyTorch 内に HIP カーネルを新しくロードするのではなく、別 EXE を呼ぶ。ComfyUI の Python・PyTorch と、Windows ネイティブホストの D3D12/HIP 依存を切り離す設計である。requirements に PyTorch を含めず、既存の GPU 用環境を置換しない。

一方、外部プロセス化はクラッシュを隔離する助けにはなるが、悪意あるバイナリを安全にするサンドボックスではない。信頼済みローカルファイルのみを人間が設定する。

やっていないこと

ゲームへの注入、画面キャプチャ、セキュリティ設定変更、管理者権限要求、ドライバー更新、DLL／モデルの自動取得、画像のクラウド送信は行わない。処理失敗時に別のアップスケーラーへ黙って切り替える動作もない。

7. 色・解像度・透過・マスク

初版の転送は RGBA8。float32 の RGB を最近傍丸めで 8 bit にし、読み戻して合成する。量子化誤差が存在するため、CPU roundtrip でわずかに画素が変わっても画質改善ではない。

GPU ホストのモデル内部 Scale と、出力解像度の倍率は別物。本版は元サイズを維持する。mix は原画像と処理結果の合成率であり、学習モデル内部の強度でもアップスケール率でもない。

HDR、linear-light 動画、BT.2020 動画は明示的に拒否する。CLI の ICC つき静止画も、自動で正しい色変換をしたふりをせず、先に明示的な SDR/sRGB 変換を求める。ComfyUI の IMAGE には元の ICC 情報が必ずしも残らないので、ノード側で色域を自動検出できるとは主張しない。

透過は原本の alpha を維持し、GPU には不透明 RGB として渡す。透明領域の RGB に定義済みの背景があるとは仮定しない。商品合成などは適切な背景・マスクを用いて評価する。

既定のネイティブ入力範囲は幅 1920・高さ 1080 以下、両辺偶数かつ 16 以上。これは本ブリッジの慎重な初期設定であり、GPU の絶対的な上限ではない。縦長 1024×1280 のイラストは初期設定の範囲外となる。形を崩して自動縮小することはしない。

8. 動画の正しさ

動画では見た目だけでなく、フレームが入れ替わる・欠ける・音がずれる、という失敗を防ぐ必要がある。

実装では FFprobe によりフレーム数・FPS・開始時刻・画面回転・色関連情報を調べ、フレームの実タイムスタンプが CFR の格子に収まるかも確認する。複数映像ストリーム、添付カバー画像、可変フレームレート、非対応の時刻オフセットは拒否する。

短い素材を RGBA8 に展開し、指定枚数ずつ処理する。最終出力は FFV1/RGB8 の MKV。映像は意図しない非可逆圧縮を挟まず、音声は再エンコードせずコピーし、音声ペイロードの SHA-256 を比較する。

音声ペイロード一致は、音声タイムスタンプの独立検証ではない。 現版はこの点を JSON に false と記録する。字幕、チャプター、編集ソフト独自メタデータの保存も対象外。商品としての動画対応には、再生確認と音声同期の検証ゲートが必要である。

容量の概算

非圧縮 RGBA8 は 幅 × 高さ × 4 × フレーム数 bytes。

1920×1080、24 fps、5 秒では、1 本の raw データだけで約 0.927 GiB。入力と出力だけでも約 1.854 GiB になる。加えてエンコード、公開前コピー、モデルの一時コピー、ログの容量が必要になる。この値は単純なサイズ式による計算であり、実測ディスク使用量ではない。

今回の実装は空き容量に余裕がないと開始しない。C: の容量が少ない環境では、十分な空きのあるローカル NTFS 作業フォルダーを明示的に指定する。長尺へ進める前に中間データを逐次流す設計へ更新する必要がある。

9. 安全性と証拠

設定ファイルはサーバー側だけに置き、ワークフローに任意の実行コマンドや DLL パスを持たせない。各ファイルの SHA-256 を固定し、コピー後のハッシュも確認する。設定を自動生成した直後は無効であり、人間が利用権限・出所を確認して有効化する。

出力は「処理終了コード 0」「enabled/completed が true」「正確なフレーム数」「所定の完了記録」「期待する raw byte 数」を満たしたときだけ採用する。異常な JSON、重複キー、古い残骸、途中ファイルを拒否する。

ハッシュは改変検知の手段であり、発行者の正当性やソースとバイナリの一致を自動証明するものではない。ネイティブホストが返す JSON も、それ単独では暗号学的な GPU 証明にならない。本版はその限界を記録する。

実行中止時にはプロセス群を終了させ、不完全な映像を最終出力として公開しない。既存の画像・動画は上書きしない。作業ディレクトリの排他ロックは、同じ作業ルート内のジョブを直列化する。別ルートや外部アプリによる GPU 競合まで防ぐものではない。

10. ライセンスと配布方針

本リポジトリのオリジナルコードは MIT。外部ホスト、AMD 実行ランタイム、NVIDIA DLL、抽出済みモデルはそれぞれ別の権利確認が必要である。公開コードの MIT ライセンスだけを根拠に、NVIDIA の重みの再配布が許されると判断してはいけない。[S02, S06–S08]

今回の ZIP には外部 DLL、EXE、重み、ONNX、GPU カーネル、元ゲーム素材を含めない。利用者が正当な権限を持つローカルファイルを設定する方式とした。取得・抽出・利用・再配布の可否はこのレポートでは確定していない。公開バイナリ配布やモデル同梱を始める前に、対象ごとの条件を確認する。

lmxxf 系では MIT の実装と、GPL のホストや外部フレームワークを組み合わせる経路がある。高速化に採用する部分を選んだ時点で、依存関係単位のライセンス表を更新する。[S05, S06]

11. 今回の検証と残ったゲート

初回納品時点の自動テスト記録は evidence/test-summary.json、個別結果は evidence/junit.xml、実行ログは evidence/pytest.log にある。カバレッジは evidence/coverage-summary.txt と evidence/coverage.json。これらは 2026-09-25 の記録であり、その後の実機検証や現在のテスト件数を示さない。

実 FFmpeg テストでは、合成した 6 フレームの短い SDR 動画に PCM 音声を付け、チャンク 1・2・4 で処理した。CPU reference 経路の画素とフレーム順序を元データと比較し、音声ペイロードをハッシュ照合する。これはファイル処理経路の検証である。

ネイティブ経路の単体テストは、明示的な偽エンジンを使う。テストダブルは正しい／壊れた JSON、短い raw、途中終了などを作り、ブリッジの判断を検証するためのもの。実 DLSS 推論や GPU 対応の証拠として数えない。

未実施の項目は、Windows ビルド、ネイティブ DLL ロード、9070 XT の実行、実 ComfyUI UI、画質、ちらつき、GPU 性能、長時間安定性である。これらを別々の完了条件にしたのが ROADMAP.md である。

12. 採用判断と次の一手

まず 9070 XT 上で 1 枚を正しく処理できることを確認する。次に 6 / 24 / 120 フレームへ進む。処理が完了しても、質感や輪郭を人間が A/B 評価して不適切なら、その素材では使わない。

その後、lmxxf の C ABI を扱う専用 D3D12 ホストを研究する。Create/PrepareFrame/RecordInputs/EnqueueHip/RecordOutputs/Poll/Retire などの GPU リソース管理が必要であり、NumPy のポインターを ctypes に渡すだけでは済まない。[S06]

ONNX の別枝は、固定サイズ・linear RGB・GPU provider・数値比較・権利確認を先に解決する。FSR などの時間型超解像も、本物の補助入力とリセット条件を設計してから扱う。FSR 3.1.4 の公式入力契約は、その必要性を考える参考になるが、すべての FSR4 実装へそのまま一般化しない。[S08, S10]

この成果物の到達点は、実行証拠と失敗条件を持つ開発用ブリッジである。次の到達点は、ひろなおの 9070 XT で同じ契約を満たす実行記録を得ること。その後に、速さと画質を競う。

目的

完了内容

合格条件

  • 外部ホストの exact CLI と INI が、実際のコード／資料に対応する。
  • NR、SR、補間、出力合成を分けている。
  • 作者の測定・こちらの測定・推論を区別している。
  • ZIP に外部 DLL・重みがない。

残すリスク

R2 — Windows / RX 9070 XT の first-light

先行条件

R1 合格。既存 ComfyUI の Python と GPU 用 PyTorch を壊さない。正当な権限のある対応ランタイムを人間が用意する。作業先と出力先に十分な空き容量がある。

R2.1 ソースとビルド

  1. fetch_upstream.py で固定コミットを取得し、レビューする。自動でコードは実行しない。
  2. x64 Developer PowerShell から build_native.ps1 を実行する。
  3. ビルドした EXE、ソースコミット、Windows SDK、MSVC、CMake、Python、OS ビルドを記録する。
  4. EXE・DLL・重みの SHA-256 を init-config で取得。生成直後は無効のまま。

合格: 固定ソースのビルドが成功し、生成物と設定のハッシュが一致。外部ランタイムがどの GPU/版を対象とするか確認済み。ビルド成功だけで GPU 対応を宣言しない。

失敗時: エラーを保存し、SDK/ツールチェーンまたはソース契約の問題として切り分ける。未確認バイナリで穴埋めしない。

R2.2 1 フレームの native 実行

自分が利用権限を持つ、特徴のある SDR 写真を使う。最初は 640×360 など、作者の検証に近い偶数サイズに明示変換する。flat/black だけを最初の試験にしない。既定は mix=1、fast_isolated=false、Temporal=0。

GPU の HIP index は機械ごとに確認する。1 を決め打ちしない。ログが RX 9070 XT を示していることと、正しい完了記録を確認する。

合格: EXE の exit 0、各カウント 1、所定の完了証拠、出力バイト数一致、真っ黒化なし、画像順序・向き・色の目視確認。manifest.json と hash 一式を保存。

注意: ピクセルが変わっただけで合格しない。完了 JSON はホストの報告であり、ソース由来と GPU 実行の独立検証は別の証拠として管理する。

R2.3 失敗経路

ランタイム不足、意図的なローカルコピーのハッシュ不一致、不正設定、GPU index の誤り、ユーザー中止、処理時間超過を試す。元の正当な DLL を改変せず、テスト用コピー／設定で行う。

合格: 正常画像を装う出力が出ない。原本が変わらない。子プロセスが残らず、次の正しいジョブが動く。失敗理由が読める。

出口

evidence/hardware/R2/ に手動の環境票、公開可能なログ抜粋、測定値を保存する。私物画像・DLL・重み・個人パスは公開しない。このゲート通過後に初めて「9070 XT で 1 枚の実行確認済み」と表現する。

R3 — ComfyUI 実行と短い動画

R3.1 ComfyUI の実接続

実際の custom_nodes フォルダーに配置し、起動ログ、9 ノードの一覧、サンプル JSON の読み込みを確認する。classic API の対応版を記録し、V3 移行を勝手に同時進行しない。

合格: CPU 診断 workflow が動作。ネイティブ workflow が R2 と同じ入力・設定で同等の出力を返す。更新したランタイムや設定で古い Comfy キャッシュを無条件に再利用しない。キュー中止が伝わる。

R3.2 バッチと素材境界

同一画像 A を連続処理し、A→B→A の順でも A の結果が他フレームに混ざらないことを確認。別解像度、別バッチ、別ジョブ間の状態混入を試す。1、2、4 枚のバッチを比較する。

合格: 順序とフレーム数の完全一致。前フレームの取り違えゼロ。OOM 時は理由を示して停止。原画像の保持とメモリ解放を確認。

R3.3 動画 6 → 24 → 120 フレーム

単一ショット、パン、被写体運動、カット切替のある短い SDR/CFR 素材を用意する。最初は chunk_frames=1。動画の長さを勝手に短くせず、必要なら事前に明示トリムする。

合格: 動画フレーム数、実 FPS、元との順序、音声ストリーム数、音声ペイロード SHA が一致。実際に再生し、同期と変形を確認する。保存失敗時に公開済みの正常なファイル名へ途中データが残らない。

未実装で追加が必要な項目

音声 packet timestamp/duration と相対 AV 同期の独立照合。現在はペイロード hash と開始時刻制約まで。コーデック／コンテナーごとの違いを試験し、ずれを検出できないまま「音声完全保持」と広告しない。

出口

静止画と短い SDR/CFR 動画だけを対象に、hardware-tested alpha を検討できる。時間方向の NR 履歴や長尺対応を主張しない。

R4 — 画質、意味保持、時間安定性

評価セット案

静止画は最低 30 素材を目安にし、写真、人物、商品／ロゴ、小さい文字、アニメ線画、暗部／グラデーションを分ける。動画は最低 12 クリップを目安にし、パン、細い線、髪、葉、反射、水面、カットを含める。これは今後の評価設計の目標であり、現在のテスト数ではない。

他人の写真やブランド素材を無断で公開用ベンチに使わない。入力の hash と利用条件を保存し、非公開素材はローカル評価だけにする。

比較の順序

A=原本、B=NR なしの同じ転送・符号化、C=NR 有効、D=別の超解像のみ、E=NR＋同じ超解像。最終解像度・色変換・符号化設定を合わせ、名前を隠してランダム順で比較する。単に C を A より大きく表示しない。

判定軸

  • 細部が見やすいか。過剰なノイズ・輪郭強調になっていないか。
  • 顔、衣服、商品形状、文字、ロゴ、線画の意味が保たれているか。
  • 暗部の粒状化、肌の不自然さ、色相ずれ、ハローが増えていないか。
  • 動画でフレーム間の粒状化・漂い・形状変化が目立たないか。

合格条件の考え方

重大なロゴ／文字／商品形状の変更を見逃して「商用素材全般に向く」と言わない。ジャンルごとに採用可否を決める。平均スコアが高くても重大欠陥は別項目として止める。mix を下げる提案も、比較を通してからプリセット化する。

PSNR や画素差は、正解画像のない NR で単独の品質点にしない。PSNR は高速版と基準版の数値回帰、画素差は無変化・過大変化の診断として用いる。

出口

「この素材群・設定・環境で、どう良く／悪くなったか」を示せる。万能アップスケーラーとして宣伝せず、不得意分野も明記する。

R5 — 性能改善と持続セッション

R5.0 計測を先に実装

warmup と本測定を分ける。入力 640×360、1280×720、1920×1080 を明示し、同じ GPU、ドライバー、モデル、出力方式で比較する。各条件を複数回測り中央値とばらつきを残す。

1 枚、24 枚、120 枚、cold/warm の全工程を分け、GPU 時間は fence/event で完了まで測る。Python 関数が返った時刻だけで GPU カーネル速度を算出しない。

R5.1 fast-isolated の検証

すでに存在する fast 経路を、新しい exact runtime/engine hash の組合せごとに検証する。速度とともに R2/R3 の出力と失敗処理を比較する。問題がなければその組合せだけを許可する。

合格: 実際に短縮した全工程時間を示せる。フレームの取り違えなし。黒崩れ・読み戻し前の未完了・子プロセス残留なし。速度改善率を事前保証しない。

R5.2 lmxxf C ABI の独立ホスト

LmxxfNrGetApi を使う専用 Windows ホストを別バックエンドとして作る。既存 eikkapine アダプターへ互換性があるふりをしない。メッセージには schema、request ID、session ID、frame ID、寸法、色契約、出力サイズ、完了状態を含める。

必要な実装は D3D12 device/queue、upload/readback buffer、resource state、producer/consumer fence、job retire、drain、error path。ヘッダーの存在だけで各 capability が実装・安定化済みだと仮定しない。

合格: 1 枚・連続 A/B/A・解像度変更・cancel・device-lost のすべてで出力の帰属が明確。逐次実行を先に通し、並列化は後にする。持続化による実測改善がなければ、基準ホストを残す。

R5.3 転送と一時容量

モデルのロードを再利用し、次に named pipe／共有メモリの制御された通信を検討する。最後に GPU interop を考える。D3D12 と PyTorch の所有権・同期・対応 ABI を検証するまでは zero-copy と呼ばない。

動画は decode→bounded queue→process→encode に移行して、一時ディスクを動画長に比例させない。ただし stdout/stderr のデッドロック、backpressure、キャンセル、音声 mux、失敗時の未公開出力を先に設計する。

R5.4 メモリ安定性

長時間の実行・中止・再実行を繰り返す。ピークと終了後の RAM/VRAM を記録し、単調な増加があれば公開を止める。ComfyUI の生成モデルと競合する場合は、ユーザー確認のある unload/scheduling を検討する。GPU 全体を勝手に独占しない。

R6 — 配布品質と公開

必須ゲート

Windows 上の新規導入、通常の ComfyUI、Portable など実際に対象にする環境を限定して試験する。対応表に exact OS、ドライバー、Python、PyTorch、Comfy commit、host/runtime hash を載せる。

CI は CPU 契約テストと Windows のビルド／プロセス試験を分ける。GPU テストは実機 runner または人間の署名付き確認として扱い、通常の GitHub-hosted runner を GPU 実機と誤記しない。

LICENSE、第三者依存表、利用者向け設定説明、アンインストール方法、既知の問題、トラブルシュート、再現ログの匿名化方法を整える。バイナリ配布の前に出所・ライセンス・必要な再配布条件を確認する。

公開時の表現

許可する表現は実際のゲートに一致させる。「CPU テスト済み」「RX 9070 XT/指定環境で静止画試験済み」「短い SDR 動画で検証済み」など。

避ける表現は「全 AMD 対応」「どんな動画でも最高画質」「ネイティブ DLSS 完全対応」「4K リアルタイム保証」「重みを自由に再配布できる」。

2. 別研究枝の扱い

ONNX / MIGraphX

固定 256×256 のモデルを、何も説明せず高解像度画像にタイル適用しない。グローバルな文脈とパディング、ノイズ、色空間、継ぎ目を個別に検証する。CPU fallback を GPU 推論と偽らない。Linux/890M の測定を Windows/9070 XT に転用しない。モデルの利用・配布条件を確認するまで本体に同梱しない。

FSR / temporal SR

光学フロー推定値とゲーム由来 motion vectors は同じ精度・意味とは限らない。depth、jitter、exposure、reset、disocclusion をどう供給するか決める。情報不足なら、対応する spatial SR として正直に独立させる。初期 NR ノードの必須依存にしない。

高ビット深度 / HDR

8 bit ブリッジとは別契約にする。RGBA16F、linear/scRGB/PQ/HLG、tone map と display transform を明確にする。相互に変換できたことと、画質が保持できたことを分けて試験する。
